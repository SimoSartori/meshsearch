# Changelog

## Unreleased

### Changed

- Radius queries (`closeObjects`, `countObjects`) skip in bulk the cells of
  each shell that cannot hold a result, instead of testing them one by one.
  The gain is largest at radii close to a multiple of the cell side.
- Count and close queries with a radius of several cell sides accept or skip
  whole cells without testing each object, where the cells are dense enough
  for this to pay.
- Large `closeObjects` batches build their output with less copying and less
  memory; the gain is largest on clustered data.
- With Clang, `nearestObject` is about twice as fast on clustered data and
  slightly slower on uniform data; with GCC it is unchanged.

Results and their order are unchanged by all of the above. Measured
timings are in the benchmark page.

### Fixed

- An index batch may answer into the container holding its indices for every
  batch form: `closeObjects(b.indices, R, b)` returned undefined results
  before. Only `nearestObject` and `nearestObjects` allowed it.


## 0.3.0 — 2026-11-25

### Breaking

Code written for 0.2 needs these changes:

| 0.2 | 0.3 |
|---|---|
| C++ `MeshGrid(X, Y, Z, cellsize, limits)`, limits a `std::vector<std::vector<double>>` | `MeshGrid::Options opt; opt.limits = std::array<std::array<double,2>,3>{{{xlo,xhi}, {ylo,yhi}, {zlo,zhi}}};` then `MeshGrid(X, Y, Z, cellsize, opt)` |
| C++ `get_lims()` returning `std::vector<std::vector<double>>` | returns `std::array<std::array<double,2>,3>`; zeros on a default-constructed grid |
| C++ `get_Cell`, `get_CellCoords`, `get_ObjectsInCell` | `get_cell`, `get_cellCoords`, `get_objectsInCell` |
| C++ deriving from `MeshGrid`, or using `GridOffset` and the protected members | not possible: `MeshGrid` is `final`, and they are private |
| Python `MeshGrid(x, y, z, cellsize, limits)` | `MeshGrid(x, y, z, cellsize, limits=limits)`: `limits` is keyword-only |
| Python batched `close_objects` offsets of dtype `uint32` | `int64` |
| Python `TypeError` for a negative index | `meshsearch.IndexError`; a negative `n` raises `meshsearch.Error` |
| Python 3.9 | Python 3.10 or later |

- A batch whose arguments the grid refuses regardless of the points (an `n`
  above the number of objects, invalid radii, an empty grid for
  `nearest_object`) now raises even when the batch is empty.
- An index of 2**32 or more raises `meshsearch.IndexError` in Python.
  `is_alive` answers `False` for it, as for any index not in the grid.

### Added

- Periodic boxes, per axis: `MeshGrid::Options` holds the `limits` and a
  per-axis `periodic` flag, read back with `get_periodic()`. In Python,
  `MeshGrid(x, y, z, cellsize, *, limits=None, periodic=False)`, with
  `periodic` a bool or a triple, and the property `periodic`. Distances are
  minimum-image distances, and any radius is valid. A periodic axis requires
  limits and a nonzero extent, and every period must be an integer multiple
  of the shortest. The cell side used is the largest not above the one
  requested that divides the shortest period, and is `get_cellsize()`
  (`cellsize`).
- `countObjects` (`count_objects`): the number of objects `closeObjects`
  would return, for a point or an object, without collecting them.
- Batches of every query in C++, under the same names, taking vectors of
  coordinates or of indices: `nearestObject` returns one index per query,
  `nearestObjects` `n*N`, `closeObjects` a `MeshGrid::Batch` (`indices` and
  64-bit `offsets`), `countObjects` a `std::vector<std::uint64_t>`. Results
  are in input order; a large batch is answered internally in cell order,
  which is faster.
- In C++, every query returning a container has a form writing into one
  passed as the last argument, cleared and then filled, its capacity kept.
- `contains(x, y, z)`: whether a query at the point is accepted, with a batch
  form; and a batched `isAlive` (`is_alive`). One `std::uint8_t` per entry in
  C++, a `bool` array in Python.
- Python: batches over arrays of object indices for every query;
  `count_objects` and its batches (`int64`); keyword-only `out=` on the
  batched `nearest_object`, `nearest_objects`, `count_objects`, `contains` and
  `is_alive`, an array of exactly the result's dtype and shape, never
  converted.
- Python: `meshsearch.Batch`, the named tuple `(indices, offsets)` the batched
  `close_objects` returns; it unpacks and compares as the pair it replaces.
- Python: `meshsearch.__version__`, `repr(grid)`, and `copy.copy` and
  `copy.deepcopy` of a grid.
- `meshsearch/Version.h`, generated by CMake and installed with the headers:
  `MESHSEARCH_VERSION` and `MESHSEARCH_VERSION_MAJOR`, `_MINOR`, `_PATCH`.
- Python: the module declares free-threaded support, so importing it on
  CPython 3.14t leaves the GIL disabled. Concurrent queries on one grid are
  safe; `add_object` and `remove_object` must not run alongside other use.
- Examples `example_periodic` and `example_batch`, in both languages.

### Changed

- Results are reproducible: the same input gives the same results in the same
  order, on Linux and macOS, on x86-64 and ARM, and with any number of
  threads. Which order objects take within a cell, and so the order of
  `closeObjects` and `get_objectsInCell` results, is not part of the
  interface; a change to it in a later version will be announced here.
- Python batches accept any array-like: a float64 or integer array is used as
  it is, and anything else, such as a list or a float32 array, is converted by
  numpy first. Before, points had to be a C-contiguous float64 array. An
  argument with a length selects the batch; values that are not real numbers
  (for indices, not integers) raise `TypeError`, and an array that is not
  one-dimensional raises `meshsearch.Error`. Integer indices of any dtype are
  never cast, so a value cannot wrap round to another object.
- Python batches run through the C++ batches, so a large one is answered in
  cell order; results are unchanged and in query order.
- C++ copy and move operations are explicitly defaulted: a move now transfers
  the storage instead of copying it, and leaves a grid that may only be
  destroyed or assigned to.
- The constructor raises `meshsearch::Error` for a cellsize whose reciprocal
  overflows a double, and for a box whose squared diagonal overflows a double
  (an extent of about 1e154 along an axis).
- The CMake package version file will use `SameMajorVersion` from 1.0, so a
  request for major version N accepts any N.x.y; 0.x versions keep
  `SameMinorVersion`.
- The library and the Python module are also compiled with
  `-fno-math-errno`. Results are unchanged.
- The documentation is rewritten: a guide covering the box and the fitted
  limits, the cell side, every query, batches, periodic boxes, memory,
  errors, threads and reproducibility, and a performance page measured on
  this version.

### Fixed

Each fix below can change results on the inputs it concerns.

- `nearestObject` could return an object that was not the nearest when an
  object lay within a few units in the last place of a cell face.
- `closeObjects` could miss an object at exactly `Rmax` near a cell face, and
  objects at or beyond `Rmin` when the cellsize was tiny against the
  coordinates' magnitude.
- The constructor could make the box slightly smaller than the limits given,
  and then refuse a point exactly on a limit. The box now always contains the
  limits, which can add one cell along an axis.
- Distances above about 1.3e154 overflowed; such boxes are now refused.
- A cellsize below about 5.6e-309 was undefined behaviour; it is now refused.
- Python: a batched `nearest_objects` with an `n` larger than the grid could
  fail with `MemoryError` or a wrapped size before checking `n`; it now raises
  `meshsearch.Error`.

### Build and packaging

- Building from source needs nanobind 3.1 or later, below 4 (before, 2.0 or
  later).
- The Python package declares the Free Threading classifier.

## 0.2.1 — 2026-10-20

### Changed

- `nearestObjects` (both overloads; `nearest_objects` in Python) now orders
  objects at equal distance by ascending index, and a tie at the N-th place
  keeps the lower indices. The order of ties used to come from the standard
  library's heap, so it differed between libc++ and libstdc++. Results for
  inputs with exactly tied distances change on every compiler; results
  without ties are unchanged.

## 0.2.0 — 2026-10-07

### Fixed

- Grids with more than 46,340 cells along one axis, or more generally with
  nx² + ny² + nz² above 2³¹ − 1, are now built and searched correctly. The
  cell-offset arithmetic used to overflow 32-bit integers there, which was
  undefined behaviour.
- A cellsize tiny against the box, an infinite limit or an infinite coordinate
  no longer leads to undefined behaviour while the cells are counted. Each now
  raises `meshsearch::Error` (see below).

### Changed

- The constructor now raises `meshsearch::Error`, before allocating anything,
  for:
  - a cellsize that is not finite (`+inf` used to be accepted);
  - limits that are not finite, or that have `lo > hi` on an axis;
  - a coordinate that is not finite;
  - more than 2,147,483,647 cells along an axis, or more cells or memory than
    64-bit sizes can count or address;
  - more than 4,294,967,295 objects.
- `addObject` raises `meshsearch::Error` once 4,294,967,295 indices have been
  issued.
- `std::bad_alloc` propagates untranslated, and is now documented
  (`MemoryError` in Python). An `addObject` that fails this way leaves the grid
  as it was.
- An axis of zero extent is documented: it gets one cell, with the box grown
  to one cellsize around it. This was already the behaviour.
- `GridOffset` and the protected members of `MeshGrid` are documented as
  implementation details, not part of the interface.
- **meshsearch is compiled with `-ffp-contract=off`.** Distances are no longer
  fused into FMA instructions where the compiler used to do so, which was on
  arm64 (Apple silicon, Linux aarch64). Results there may differ from 0.1.0
  at exact radius boundaries and between exactly equidistant objects. x86_64
  results are unchanged.

### Build and packaging

- CMake install rules and a package configuration:
  `find_package(meshsearch CONFIG)`, with the target `meshsearch::meshsearch`.
  That target name is also available when meshsearch is included with
  `add_subdirectory` or `FetchContent`. The `MESHSEARCH_INSTALL` option is on
  by default and off under scikit-build-core.
- As a subproject, meshsearch no longer builds its tests and example by
  default, and no longer sets `CMAKE_BUILD_TYPE`.
- The Python module no longer exports the library's C++ symbols.
- Python package metadata: SPDX licence expression (`BSD-3-Clause`), and
  Documentation, Source, Issues and Changelog URLs. Building from source needs
  scikit-build-core 0.11 or later.
